## 用户已确认的关键结论

1. **`combustible_mass` 含棉线**，样品质量 = `combustible_mass − cotton_mass`。
   验证方式：用 3000 mL 水 + 0.8282 g 苯甲酸，程序算出 **W = 3170.0 J/K**，
   与课程软件截图里的 W = 3170.0 **完全一致**。软件参数框里的 500 mL 是默认值，
   不是实际用水量（用户明确纠正过）。
2. **取点（雷诺校正区间）默认用 σ = 0.02**，不是课程软件内置的 0.005。
   本套数据升温缓慢、点火前基线有漂移，σ=0.005 会把漂移误判成平台结束，
   把拟合区间放到还在上升的曲线上（方糖那条就是典型）。
   σ=0.02 时两个样品一致性最好（0.01%）。
   用户后来对取点还有意见，程序里另备了「升温段法」「平台锚点法」两套方案。
3. **W 由苯甲酸单独标定，对它的取点极敏感**（σ 从 0.005 到 0.02，W 从 3170
   变到 4225，差 33%）。已反复提醒用户核对苯甲酸那轮的取点。

## `启动.cmd` 的坑（已修复，用户实测通过 2026-09-18）

首次交付的 `启动.cmd` 双击后报一堆 `'xxx' 不是内部或外部命令`，并且
**`run.py` 被 VS Code 打开了**。两个独立原因叠在一起：

1. **`.cmd` 内容写成了 UTF-8 中文**。cmd.exe 按 ANSI(GBK) 解码 `.cmd`，
   中文变乱码、乱码又破坏了 `if errorlevel 1 (...)` 的括号配对语法，
   于是把中文碎片当命令执行。→ **`.cmd` / `.bat` 内容一律只用 ASCII**，
   文件名 `启动.cmd` 是中文没关系。检查：
   `($bytes | Where-Object { $_ -gt 127 }).Count` 必须为 0。
2. **Python 发现逻辑不可靠 + 变量拼参数**。原来写 `set "PY=py"` 再
   `"%PY%" -3 "%~dp0run.py"`，引号错位报 `Unable to create process`；
   而一旦 `%PY%` 解析失败，命令行退化成"用默认程序打开 run.py"，
   于是 **VS Code 打开了 run.py**（而不是提示找不到 Python），极难排查。
   → 改为**先试绝对路径**（`C:\Python3xx\python.exe`、`%LOCALAPPDATA%\
   Programs\Python\Python3xx\python.exe`），再退回 PATH，且**必须
   `python -c "import sys"` 真能起来才算数**；变量只存完整 exe 路径，
   不拼参数。

完整可用写法已写进技能第 4.5 节，新增实验模块时直接复制。

## 2026-09-21 有效数字按标准重写（用户拍板：σ 一律 2 位 / 通用修约 / 全部对齐）

用户指出"最后结果的有效数字和标准差"写法不合规。查了 JJF 1059.1-2012 与
GB/T 8170-2008 之后向他确认了三个选项，选的是：

1. **不确定度一律取 2 位有效数字**（JJF 1059 只说 1~2 位，专家推荐首位 1/2 取 2 位、
   3~9 可只取 1 位；用户选"一律 2 位"）→ σ = 32.8 → 33，σ = 2.0038 → 2.0。
2. **修约用"四舍六入五成双"**（GB/T 8170），不用不确定度专用的"只进不舍"。
3. **全部对齐**：不只最终结果，中间量（ΔT、T_l/T_r、Σq_V、拟合直线的 k 和 b）也一起
   按"末位与不确定度末位对齐"写。

核心规则：**测得值的末位必须与不确定度的末位对齐**（JJF 1059.1 硬要求）。

实现：`report.py` 顶部加了 `_sig/_place/_fix` 与 `val() / unc() / pm() / pct()`
（`SIG_DIGITS = 2`），用 `decimal.ROUND_HALF_EVEN`。**正文里不要再手工 `k(x, nd)`
定小数位**，一律走这几个函数。

## 用户对报告格式的明确要求（吃过多次纠正）

- **只示出变量值的一律用普通文本，禁止用公式对象**；只有真正做计算的式子
  （含 = ± × / 等）才用公式。引用标注用上标 `^{[1]}`。
  ⚠️ **小写希腊字母是变量（斜体）**：`σ`、`ρ` 这类写在正文里也要包 ITALIC 片段
  （2026-09-20 用户在 4.2 实验讨论里抓到 `σ` 和 `R²` 漏网）。
  上标按同样规则分块：`R^{2}` = 斜体 R + 正体上标 2（`docxkit._write_script`）。
  中文之间不要空格（"测得 蔗糖" 这种），但中文接公式/数字留空格。
  → **摘要与小结里的"本实验测得……为 Q_p = Q_V = (5547 ± 11) kJ·mol⁻¹"也属于
  "只报结果"，必须用普通文本**（2026-09-18 用户第二次纠正，第一次是正文）。
- 单位正体、变量斜体、说明性下标正体、化学式下标正体。
  → **大写希腊字母也是正体**：`Δ T` 要排成"正体 Δ + 斜体 T"，`Σ q_{V}` 同理
  （2026-09-18 用户第三次纠正）。已改为自动判定：
  `docxkit._emit_text()` 里 italic run 只把拉丁字母/小写希腊字母斜体，
  `docxkit._sub_chunks()` 让多字母下标（sam、cot、Ni）与数字正体、单字母下标
  （V、p、w、r）保持斜体，混合下标逐块处理（`Q_{V-Ni}` = 斜体 V + 正体 Ni）。
  公式侧对应 `omml._simple_sub_xml()`。表头 `m_{Ni-1}/g` 按 `/` 切成变量+单位。
  **正文里直接写 `('t','m_{sam}',ITALIC)` 就行，不要再手动拆 `('t','sam',SUB)`。**
- **负号/减号要用真减号 `−`（U+2212），不是 ASCII 连字符**（用户 2026-09-18 提出）。
  普通文本已自动转换（`docxkit._minus_signs`，只换"符号位"上的连字符：
  前面不是字母数字/右括号、后面紧跟数字）。公式里的 `-` 由 Word 自己渲染成 `−`。
- **标题里的量符号也要斜体**（`3.2.2 量热计常数 W 的计算`）：`heading()` 现在
  和 `para()` 一样接受片段列表。漏网之处：表下注释里的 `W`（`注：…标定量热计常数 W`）。
- **保持正体的例外**：`电极A`/`电极B`（器件代号，讲义原文就是正体）、`B样条`、
  `GPL-3.0`、`v2.2.4`、`5-75~5-76`、`温度-时间曲线`（连接号）。
- **正文全文五号（10.5 pt），上下标也是**：上下标的字号属性直接写 10.5，
  Word 渲染时自己会缩到 ≈7 pt；若自己先缩到 7.5 pt，Word 再缩一次只剩 5 pt，
  小到看不清。Unicode 上下标（`J·g⁻¹`、`10⁻³`、`C₁₂H₂₂O₁₁`）统一转成真上下标。
- 表格五号字、单元格不换行、表头不用公式。
- 封面行数要保证摘要与关键词留在第一页，**「1 引言」另起一页（第 2 页第一行）**。
- **第 3 节逐轮小节顺序：标定轮最前，报告主角（方糖）最后**（用户 2026-09-18 选定；
  "第一轮方糖"原本排在最前，导致样品计算引用了还没标定出来的 W）。
  实验步骤 2.2 与表 1 仍按真实轮次顺序。
- 报告引言要从讲义精简成「实验目的 / 实验原理 / 实验方法」三段文字（不用扫描图），
  **但装置图要插**（2026-09-18 用户后来发来讲义装置图要求加上）：
