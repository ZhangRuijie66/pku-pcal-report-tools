改法（两个工具的 `pcal/server.py` 各一行）：

## 2026-09-23（第六轮）表 1 的 n₀ 列头是粗正体

用户发来截图：「表1里这个 n0 的正斜体还是不对」——表头里 `n` 是粗**正**体。

`docxkit.ReportBuilder._write_header()` 原来是：

```python
if '/' in text:                      # 'm_{Ni-1}/g' → 斜杠前斜体、后面正体
    sym, unit = text.split('/', 1)
    add_rich_text(p, sym, dict(base, italic=True))
    add_rich_text(p, '/' + unit, base)
else:                                # ← 'n_{0}' 掉进这里，整块正体
    add_rich_text(p, text, base)
```

**只按"有没有 `/`"判断，于是"没有单位的表头"整块漏了斜体。**
溶解热的表 1 末列是 `n_{0}`（浓度比，无量纲）、表 3 首列也是 `n_{0}`，
两处都成了粗正体（表 2 / 表 4 每列都带单位，所以没露）。

→ 判据改成看内容：

```python
elif re.search(r'[A-Za-zα-ω]', text):     # 出现拉丁字母/小写希腊字母 = 量符号
    add_rich_text(p, text, dict(base, italic=True))
else:                                     # 纯中文（编号、用途、来源）才正体
    add_rich_text(p, text, base)
```

改完表头全部正确：`*n*₀`、`Δ *m*/g`、`*m*/g`、`*n*₂/mol`、
`*q_d*/(J·mol⁻¹)`、`*Q_d*/(kJ·mol⁻¹)`，`编号`/`来源` 仍是正体。

用户：「又踩坑了，分子量的表示不应该用公式，应该是普通文本。」

`M(H₂O)=18.015 g·mol⁻¹  M(KNO₃)=101.102 g·mol⁻¹` 当时是 `rb.equation()`。
这条规则技能里写了两次（§3.1 的表格里就摆着 `M_r = 342.296 g·mol⁻¹` →

顺手把同类的另外三处也改了（凡是"段末说……为："然后跟一条 `变量 = 数值` 的
居中公式，基本都中招）：

| 原来 | 现在 |
| --- | --- |
| `M(H₂O)=…` / `M(KNO₃)=…` 公式 | 普通文本：`M`(斜) `(H₂O)`(正) `= 18.015 g·mol⁻¹，` … |

| `t=92.398\ s,\qquad t'=392.779\ s` | 并进句子：「……横坐标分别为 t = 92.398 s、t′ = 392.779 s。」 |
| `R^{2}=0.95380`、`Q_{s}^{0}=…`、`a=…` 三条 | 并进一句：「可见拟合相关性较好，相关系数 R² = 0.95380。对应于各参数，即 Q_s⁰ = (37.65 ± 0.17) kJ·mol⁻¹，a = 0.324 ± 0.037。」 |

保留为公式的：定义式（`n₀=n₁/n₂`、`q_d=…`、`Q_d=…`）、代入数值的完整计算

## 2026-09-23（第三轮）公式的正斜体 / 上下标排查 —— 修了 omml.py 的三个真 bug

用户反馈「检查公式，上下标、正斜体，仍有问题」。写了两把新尺子来查：

- `_pcal_tools\mathcheck.py`：把 docx 里每个 `m:oMath` 展开成
  「文本 + `[I]/[R]/?` + `[sub]/[sup]`」的序列（`[?]` = 没写样式、走 Word 数学区默认斜体）。
  **段落级的 `romancheck.py` 看不到公式**，必须用这个。
- `_pcal_tools\mathupright.py`：审计公式里所有**显式正体**的 run。

最终 1054 个公式 run：显式正体的只有数字、运算符、`Δ`、`∑`、单位（kJ/mol/g/K/s/J）、
`mol⁻¹` 的 `-1`、化学式的 H/O/N —— 没有漏网的变量。段落级也干净
（`romancheck` 只剩单位、化学式、参考文献里的英文、`Langmuir`、`GPL-3.0`）。

### omml.py 的三个 bug（都真实影响渲染）

1. **`\frac{m}{M(KNO_{3})}` 被切坏。**
   `to_omml_body` 会先把 LaTeX 按「化学式」切成 `tex/chem` 片段再分别解析。
   在 `KNO_{3}` 处切开后，前一段是 `\frac{m}{M(` ——**第二个花括号没闭合**，
   于是分母只剩 `M(`，`KNO_{3})` 掉到分数线外面，PDF 里印成
   `n₂ = m/M( KNO₃}) = …`。
   → 切分前先检查 `latex[pos:i]` 的花括号是否配对（`_braces_balanced`）；
   同时**教会解析器自己认化学式**（`parse_unit` 里对 ASCII 大写字母先试
   `_is_chem_span`），切不了就整段交给解析器也不会把 KNO₃ 排成斜体。
2. **数学区里裸露的空格被保留成窄空格。** 结果 `\Delta Q` 印成「Δ Q」、
   `\Delta\Delta T` 印成「ΔΔ T」、`\Delta m` 印成「Δ m」——参考报告里都是紧挨着的。
   → LaTeX 语义本来就忽略数学模式里的空格，直接丢掉；要留空格就写 `\ `（`\quad` 等照旧）。
3. **非 ASCII 字母一律被排成正体。** `sty = 'i' if (c.isalpha() and c.isascii()) else 'p'`
   把小写希腊字母也判成正体，于是 `σ`、`ρ` 全是正体；
   而参考报告里 Word 的默认是小写希腊字母斜体（`ρ[?]`）。
   → 新增 `_math_sty()`：**大写希腊字母正体（Δ、Σ），其余字母（拉丁 + 小写希腊）斜体**。

这三处**同步到了燃烧热工具的那份 `omml.py`**（两份文件除这三处外完全相同），
燃烧热报告重新生成后公式渲染无回归（`Q_V = −C_VΔT`、`m_Ni = m_Ni-1 − m_Ni-2` 都正常）。

### report.py 里的三处（非公式侧）

1. **四个标题里的量符号是正体**：`3.2.1 …Δ Q 及积分溶解热 Q_{s}`、`3.2.2 …`、
   `3.3.1 Q_{s}-n_{0} …`、`4.3.1 …d Δ Q` 当时是按**字符串**传给 `heading()` 的，
   于是整段走正体。→ 改成片段列表，量符号包 `ITALIC`。
   （技能 §3.2 早就写了「标题里的量符号也要斜体」，这次是漏做。）
2. **2.1.2 试剂的「硝酸钾 KNO3」没有下标**（`SUBSTANCES['kno3']['label']` 里是 ASCII `KNO3`）。
   → 报告里改成用「中文名 + `tex_label`」拼，得到真下标 KNO₃。
3. **4.4 里写成了 `0.1%%`**，那段 `rb.para` 没走 `%` 格式化，于是原样印出两个百分号。→ 改回 `0.1%`。

### 一条经验

`omml.py` 里的 `[?]`（不写 `m:sty`）是**故意的**：Word 数学区默认就按变量排斜体，
显式写 `m:sty val="i"` 反而多余。所以判断「这个 run 该不该斜体」要按
**语义**看（是变量还是单位/化学式/常数），不能看有没有 `<w:i/>`。
参考报告（用户自己那份）里的公式也是这样：`Δ[R] m[?]`、`ρ[?]`、`M[?]`。

   Word 导 PDF 时四级也照样进了书签树。
3. **表4 的「相对贡献/%」原来各列都除以合成值，加起来 200% 很怪**；
   改成**方差占比**（v²/σ²），五项加起来正好 100%。
4. **`σ_Qs` 的单位错了一次**：分子用了 kJ、分母是 mol，却按 J·mol⁻¹ 印出去
   （594 J·mol⁻¹ 应为 0.59 kJ·mol⁻¹）。写公式时分子分母的单位要一起盯。

### 数据本身的一个发现（重要，已如实写进 3.2.2）

**中间平台（B）的线性很差**：六轮的 B 段 R² 只有 0.408 / 0.842 / 0.618 /
0.835 / 0.767 / 0.875，而两端平台都在 0.87~0.97。原因不是取点不当：

- 溶解降温之后温度还在缓慢弛豫上升，平台 B 与通电升温段**在时间上部分重叠**，
  本套数据里根本没有一段真正平直的低温柔台；
- 试过把 End2 往左挪到加热开始前 10 个点，B 的 R² 反而掉到 0.21~0.76
  （窗口越短越吃不到那段近似直线的弛豫），Qs0 只从 37.65 变到 37.41。

所以**保持软件记录的取点不动**（也正好复现软件的 Q），
在 3.2.2 里加了一句说明：两次校正共用同一条 B 直线，
B 的偏差在很大程度上相互抵消，对结果的影响远小于 R² 看上去的程度。

## 关键决定

1. **默认取点用 `dissolution.csv` 里记的，不用自动寻点。**
   数据目录里那份 `dissolution.csv` 是课程软件导出的，逐轮记录了用户当时在软件里
   选定的 6 个下标（`Start 1`…`End 3`），是最权威的复现依据。
   `pcal/dissolution.py: parse_summary_csv` 读它，`server._software_summary` 提供给前端，
   前端在生成轮次时把 `points` 填进去。界面上可切换成「按曲线自动寻点」。
   —— 这与燃烧热工具的做法（自动寻点为主）不同，那边的自动取点与手选差 28%，
   这边刚好有软件留下的记录可用，没必要冒这个风险。

2. **自动寻点是兜底，按物理事件识别，不用滑动窗口标准差。**
   课程软件的 `find_start_end_point` 是滑动窗口标准差判据（count=6），
   逻辑绕且只吐 5 个点，不适合溶解热。本模块改成：
     · 平滑导数找「溶解降温段」与「通电升温段」；
     · 三个平台各自在允许区间里取**残差标准差最小的窗口**；
     · 只要残差不超过最优值的 1.3 倍，就取**离过渡段最近**的窗口
       （缩短雷诺校正的直线外推距离）；
     · 加热起止时刻 `t1`、`t2`（csv 头里有）用来限定中间平台与终末平台的范围，
       比导数阈值可靠。
   自动取点与软件取点的 Q 差 1~3%，只作兜底。

3. **不确定度模型以电流为主。**
   `σ_Q/Q = √[(2σ_I/I)² + (σ_R/R)² + (σ_t/Δt)² + (σ_ΔTd/ΔTd)² + (σ_ΔTh/ΔTh)²]`，
   仪器允差按均匀分布取 `e/√3`，每个校正温差是两个温度之差故 `σ_ΔT=√2e/√3`。
   代入 e_I=0.01 A、e_R=0.02 Ω、e_t=0.2 s、e_T=0.002 K：
   电流项 1.14%、电阻项 0.11%、计时项 0.03%、两个温差项各约 0.086%，
   合成 ≈ 1.2%（σ_Q ≈ 0.051 kJ）。**电流项主导**——这也正好回答了讲义的
   「加热器功率过高或过低会有什么影响」，报告 4.2.4 里就是这么写的。
   e_I 可在界面上改（不同电流表允差不同）。

4. **讲义没有给硝酸钾溶解热的文献值**，所以报告 4.1 没有硬套一个文献对比，
   而是用 `R²` 与不确定度自洽性作为判据；界面上留了「文献 Qs⁰」输入框，
   老师给了值就填上，报告会自动加一句相对偏差。

## 排版上这次新加的东西（已回写进技能）

1. **表头行必须 `w:tblHeader`、每行必须 `w:cantSplit`。**
   原先表格跨页时，「第3轮」被从中间劈成「第3」在上一页、「轮」在下一页，
   而且续页的表头只重复出第一格 —— 就是行被劈开造成的。
   `docxkit.ReportBuilder._row_props()` 现在给首行加 `w:tblHeader`、
   给所有行加 `w:cantSplit`。
2. **题注与图片要 `w:keepNext`。**
   否则「表3 经验方程的拟合参数」会孤零零留在页底，表格跑到下一页。
   `docxkit.caption()` 与 `docxkit.figure()` 现在默认加 `keepNext`。
3. **题注里也会出现量符号（`Q_s`、`n_0`）**，所以 `caption()` 改用
   `add_rich_text` 写正文部分，真上下标 + 变量斜体。
   —— 注意图题里**不能写 `$...$`**，那是给 matplotlib 的；
   第一版写成 `'图1  $Q_{s}$-$n_{0}$ …'`，PDF 里就原样印出了美元符号。
4. **表宽与列宽的复核**：表1 的「轮次」列 1.25 cm 装不下「第3轮」（需 1.7 cm），
   会被挤到换行。凡是新表，列宽都要按最宽内容（3 个汉字 ≈ 1.1 cm + 0.18 cm 内边距）
   留够。
